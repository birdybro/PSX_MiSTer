# Clock Domain Crossing (CDC) Analysis — PSX_MiSTer

## Clock Domains

All clocks derive from a 50 MHz reference (`CLK_50M`):

| Clock     | Source | Approx. Frequency | Domain Role                     |
|-----------|--------|--------------------|---------------------------------|
| `clk_1x`  | PLL    | ~33.87 MHz         | PSX system clock (CPU, bus, I/O)|
| `clk_2x`  | PLL    | ~67.74 MHz         | GPU, memory, savestates, SPU RAM|
| `clk_3x`  | PLL    | ~101.6 MHz         | SDRAM controller                |
| `clk_vid` | PLL2   | Variable (PAL/NTSC)| Video output                    |
| `CLK_50M` | Board  | 50 MHz             | PLL configuration               |

`clk_1x`, `clk_2x`, and `clk_3x` are generated by the same PLL (phase-aligned, integer-related). `clk_vid` is generated by a separate PLL2 and is **truly asynchronous** to the other clocks.

## CDC Instances Found

### 1. PSX.sv — PLL Reconfiguration (CLK_50M ↔ clk_1x) — Lines 265–308

**Mechanism:** 2-FF synchronizer chains

```systemverilog
pald  <= isPal;        // isPal from clk_1x domain
pald2 <= pald;         // 2nd stage
// same for syncVideoClock → pdbg/pdbg2, fast_forward → pffw/pffw2
```

Edge detection (`pald2 != pald`) triggers a state machine to reconfigure PLL2 dividers.

**Assessment:** **Safe.** Standard 2-FF synchronization with edge detection. These are slow-changing control signals.

---

### 2. PSX.sv — Video Output (clk_1x → clk_vid) — Lines 1628–1677

**Mechanism:** None — direct sampling

The `always_ff @(posedge CLK_VIDEO)` block at line 1628 directly samples signals originating from the `clk_1x`/`clk_vid` pipeline inside `psx_mister`:

- `hs`, `vs`, `hbl`, `vbl` — sync/blanking
- `r`, `g`, `b` — pixel data (8 bits each)
- `video_interlace`, `video_isPal` — mode signals
- `video_hResMode` — resolution mode (3 bits)

**Assessment:** **Low risk in practice.** These signals are produced by `gpu_videoout` which operates in the `clkvid` domain internally (via `gpu_videoout_async`). By the time they reach `PSX.sv`, they are already in the `clk_vid` domain. The apparent CDC is actually same-domain since `CLK_VIDEO = clk_vid` (line 1515). However, `video_isPal` originates from `clk_1x` and is used directly in the `CLK_VIDEO` block (lines 1638, 1659, 1667) without resynchronization.

**Improvement opportunity:**
- Add a 2-FF synchronizer for `video_isPal` before use in the `CLK_VIDEO` domain. This signal changes extremely rarely (only on region change), so the risk is low, but proper synchronization would eliminate any metastability window.

---

### 3. PSX.sv — Status Bits in Video Domain — Lines 1674–1675

**Mechanism:** None — direct combinational use

```systemverilog
if (status[62] || hack_480p || (status[54:53] > 0))
    video_aspect.hb <= hbl;
```

`status[]` is loaded via `hps_io` in the `clk_1x` domain. `hack_480p` is `status[89]`. These are used directly in the `CLK_VIDEO` always_ff block.

**Assessment:** **Low risk.** These are quasi-static configuration signals that change only via OSD menu interaction. Metastability is theoretically possible but extremely unlikely to cause visible issues.

**Improvement opportunity:**
- Register `status[62]`, `status[54:53]`, and `status[89]` through a 2-FF synchronizer into the `clk_vid` domain if robustness is desired.

---

### 4. PSX.sv — fast_forward in Video Domain — Line 1640

**Mechanism:** None

```systemverilog
VGA_DISABLE <= fast_forward;   // clk_1x signal sampled in CLK_VIDEO
```

`fast_forward` is generated in the `clk_1x` domain (line 313).

**Assessment:** **Low risk.** Single-bit signal, changes infrequently. Worst case is a single frame of incorrect VGA_DISABLE state.

**Improvement opportunity:**
- Synchronize `fast_forward` into `clk_vid` with a 2-FF chain before assignment to `VGA_DISABLE`.

---

### 5. PSX.sv — Heartbeat (HPS → clk_1x) — Lines 1022–1031

**Mechanism:** 1-FF only

```systemverilog
heartbeat_1 <= heartbeat;
if (heartbeat == heartbeat_1) begin  // stale detection
```

`heartbeat` comes from `hps_io` which itself operates on `clk_1x`, so this may actually be same-domain. However, the HPS interface ultimately bridges from the ARM HPS clock domain, and `hps_io` provides synchronization internally.

**Assessment:** **Safe** if `hps_io` properly synchronizes `heartbeat` into `clk_1x` before output (which the MiSTer framework does). The 1-FF here is for edge/change detection, not CDC.

---

### 6. PSX.sv — SNAC Inputs (External async → clk_1x) — Lines 1793–1806

**Mechanism:** 2-FF and 4-FF synchronizer chains with glitch filtering

```systemverilog
USER_IN3_1 <= USER_IN[3];   USER_IN3_2 <= USER_IN3_1;   // 2-FF
USER_IN3_3 <= USER_IN3_2;   USER_IN3_4 <= USER_IN3_3;   // extended to 4-FF
```

Line 1806 implements glitch detection: `ackglitch <= USER_IN3_2 ^ USER_IN3_4;`

**Assessment:** **Safe.** Proper multi-stage synchronization for truly asynchronous external inputs. The 4-stage chain for `USER_IN[3]` with glitch filtering is well-engineered.

### 7. gpu_videoout_async.vhd — All Video CDC (clk1x ↔ clkvid ↔ clk2x) — Lines 170–229

**Mechanism:** 3-FF synchronizer chains throughout

**clk1x → clkvid (lines 171–200):**
- `videoout_settings` — 3-stage: `_1x → _s2 → _s1 → output`
- `ce`, `reset`, `softReset`, `savestate_pause`, `system_paused` — all 3-stage

**clkvid → clk1x (lines 202–216):**
- `videoout_reports` — 3-stage: `vid → _s1 → _s2 → _1x`
- `allowunpause` — 3-stage

**clkvid → clk2x (lines 218–229):**
- `videoout_request` — 3-stage

**Assessment:** **Safe.** This is the best-synchronized module in the design. All crossings use 3-FF chains, exceeding the typical 2-FF minimum. This is the correct approach for the truly asynchronous `clk_vid` domain.

**Note:** `videoout_settings` is a multi-bit record. A 3-FF chain on a multi-bit bus does **not** guarantee coherent transfer of all bits simultaneously — individual bits may arrive at different metastability-resolved values on different cycles. This is acceptable here because the settings are quasi-static (change only during configuration, not per-pixel) and the receiving logic tolerates brief incoherence.

**Improvement opportunity:**
- If strict coherence is ever needed, use a toggle-handshake or gray-coded transfer for `videoout_settings` and `videoout_reports`. The current approach works because these signals change slowly relative to clock frequencies.

---

### 8. gpu_videoout.vhd — Line Buffer Dual-Port RAM (clk2x → clkvid) — Lines 340–382

**Mechanism:** Dual-port RAM (dpram_dif) with independent read/write clocks

Write port clocked by `clk2x`, read port clocked by `clkvid`.

**Assessment:** **Safe.** Dual-port RAM with separate clock domains is a standard and safe CDC mechanism. The FPGA block RAM handles metastability internally. Address coordination is managed by the videoout logic.

### 9. justifier_sensor.vhd — IRQ Pulse (clkvid → clk1x) — Lines 57–67

**Mechanism:** 2-FF synchronizer (actually 3-stage with output register)

```vhdl
irq10_1   <= irq10;      -- combinational from clkvid state machine
irq10_2   <= irq10_1;
out_irq10 <= irq10_2;    -- output
```

The `irq10` signal is combinationally derived from a state machine clocked by `clkvid` (line 52: `irq10 <= '1' when (state = DRAW) else '0'`). The 2-FF chain synchronizes this level into `clk1x`.

**Assessment:** **Safe** for level synchronization. However, `irq10` is a short pulse (active during DRAW state for a few `clkvid` cycles). If a `clkvid` pulse is shorter than 2 `clk1x` periods, it could be missed entirely.

**Improvement opportunity:**
- If `clkvid` is faster than `clk1x` and the DRAW state can be brief, consider converting to a toggle-based pulse synchronizer to guarantee detection. Currently, DRAW lasts multiple `clkvid` cycles (controlled by `draw_count` counting down from 3), so the pulse width is likely sufficient, but this is worth verifying for all PAL/NTSC/resolution combinations.

### 10. savestates.vhd — Savestate Handshake (clk1x ↔ clk2x) — Lines 209–292

**Mechanism:** Direct cross-domain sampling with handshake protocol

The module has two process blocks — one on `clk1x` (line 209) and one on `clk2x` (line 264). Signals cross between them:

**clk2x → clk1x (read in clk1x process):**
- `reset_2x`, `ss_reset_2x`, `load_done_2x`, `loading_ss_2x` — control flags
- `SS_DataWrite_2x`, `SS_Adr_2x` — 32-bit data + 19-bit address
- `SS_wren_2x`, `SS_rden_2x` — write/read enables

**clk1x → clk2x (read in clk2x process):**
- `SS_DataRead` — 32-bit data
- `reset_out`, `ss_reset`, `load_done` — handshake acknowledgments
- `SPURAM_done1X`, `SPURAM_dataRead1x` — SPU RAM data

**Assessment:** **Safe by design but unconventional.** `clk1x` and `clk2x` are derived from the same PLL with an exact 2:1 ratio and are phase-aligned. The `clk2xIndex` signal (generated elsewhere) identifies which `clk2x` edge aligns with `clk1x`, enabling safe cross-domain transfers without traditional synchronizers. The handshake protocol (e.g., `clk2x` sets `reset_2x`, `clk1x` reads and acknowledges via `reset_out`, `clk2x` clears `reset_2x` when it sees the ack) ensures signals are stable when sampled.

This works correctly because the clocks have a known, fixed phase relationship. It would **not** be safe if the clocks were from different PLLs.

**Improvement opportunity:**
- Add comments documenting the assumption that `clk1x` and `clk2x` are phase-aligned from the same PLL. If this invariant is ever broken (e.g., different PLL configurations), these crossings would silently become unsafe.
- The multi-bit crossings (`SS_DataWrite_2x[31:0]`, `SS_Adr_2x[18:0]`) rely on the phase relationship for coherent transfer. If robustness against PLL changes is desired, wrap these in a proper handshake with a request/ack toggle.

### 11. sdram.sv — Toggle Synchronizer (clk_1x ↔ clk_3x) — Lines 134–159, 232–236

**Mechanism:** Toggle bit + 2-FF synchronizer

```systemverilog
// clk_base (clk_1x) domain — line 159:
clk1xToggle <= !clk1xToggle;

// clk (clk_3x) domain — lines 234-236:
clk1xToggle3X   <= clk1xToggle;      // FF1
clk1xToggle3X_1 <= clk1xToggle3X;    // FF2
clk3xIndex      <= clk1xToggle3X_1 == clk1xToggle;  // detect alignment
```

This generates `clk3xIndex` which identifies the `clk_3x` cycle that aligns with `clk_1x`, used to gate request sampling (line 238: `ch1_rq <= ch1_rq | (ch1_req & clk3xIndex)`).

**Ready signals (clk_3x → clk_1x):**
```systemverilog
// clk_base (clk_1x) domain — lines 153-155:
ch1_ready <= ch1_ready_ramclock;
ch2_ready <= ch2_ready_ramclock;
ch3_ready <= ch3_ready_ramclock;
```

These are direct 1-FF transfers from `clk_3x` to `clk_1x`.

**Assessment:** **Safe by design.** `clk_1x` and `clk_3x` are from the same PLL with a 3:1 ratio and fixed phase alignment. The toggle synchronizer correctly identifies the aligned cycle. The 1-FF ready transfers work because the signals are set in `clk_3x` and guaranteed to be stable by the time the aligned `clk_1x` edge arrives.

**Improvement opportunity:**
- The ready signal path (`ch*_ready_ramclock` → `ch*_ready`) uses only 1-FF. While safe with phase-aligned PLL clocks, adding a 2nd register stage would provide margin against routing delays and would be essentially free in terms of FPGA resources.

---

### 12. spu_ram.vhd — SPU Memory Interface (clk1x ↔ clk2x) — Lines 376–470

**Mechanism:** FIFO-based CDC and `clk2xIndex` gating

The SPU RAM module uses `clk2x` for its memory state machine while receiving requests from the `clk1x`-domain SPU core. A FIFO (`fifoOut`) bridges data between domains. The `clk2xIndex` signal is used to identify `clk2x` edges aligned with `clk1x`.

**Assessment:** **Safe.** Uses the same phase-aligned clock relationship as the savestate module. The FIFO provides proper buffering for data transfers.

---

### 13. memorymux.vhd — Unused clk2x Port

`memorymux.vhd` declares `clk2x` as an input port (line 11) but never uses it — no `rising_edge(clk2x)` exists anywhere in the file. All logic runs on `clk1x`.

**Assessment:** **No CDC concern.** The unused port is likely a leftover from a previous design iteration.

**Improvement opportunity:**
- Remove the unused `clk2x` port to avoid confusion about clock domain boundaries.

## Recommended Improvements

### High Value (correctness under all conditions)

1. **Synchronize `video_isPal` into `clk_vid` domain** (PSX.sv:1638). This is the most meaningful CDC gap — `video_isPal` genuinely originates in `clk_1x` and is used in decision logic in the `clk_vid` always_ff block. A 2-FF synchronizer eliminates the metastability window:
   ```systemverilog
   reg video_isPal_sync1, video_isPal_sync2;
   always_ff @(posedge CLK_VIDEO) begin
       video_isPal_sync1 <= video_isPal;
       video_isPal_sync2 <= video_isPal_sync1;
   end
   // Use video_isPal_sync2 instead of video_isPal in the CLK_VIDEO block
   ```

2. **Synchronize status configuration bits** used in `CLK_VIDEO` domain (PSX.sv:1674–1675). Group `status[62]`, `status[54:53]`, `status[89]` into a small register synchronized into `clk_vid`:
   ```systemverilog
   reg [3:0] vid_cfg_sync1, vid_cfg_sync2;
   always_ff @(posedge CLK_VIDEO) begin
       vid_cfg_sync1 <= {status[89], status[62], status[54:53]};
       vid_cfg_sync2 <= vid_cfg_sync1;
   end
   ```

3. **Synchronize `fast_forward` for `VGA_DISABLE`** (PSX.sv:1640). Simple 2-FF synchronizer.

### Medium Value (robustness/maintainability)

4. **Document phase-alignment assumptions** in `savestates.vhd` and `sdram.sv`. Add comments at each cross-domain signal access stating the requirement that clk1x/clk2x (or clk1x/clk3x) must be phase-aligned outputs of the same PLL. This prevents future maintainers from introducing bugs if the PLL configuration changes.

5. **Add 2nd register stage for SDRAM ready signals** (`sdram.sv:153–155`). The `ch*_ready_ramclock → ch*_ready` path uses 1 FF for a `clk_3x → clk_1x` crossing. While safe with PLL alignment, a 2nd FF adds margin for essentially zero cost.

6. **Verify justifier IRQ pulse width** (`justifier_sensor.vhd`). Confirm that the DRAW state lasts at least 2 `clk1x` periods across all video modes. If not, convert to a toggle-based pulse synchronizer.

### Low Value (cleanup)

7. **Remove unused `clk2x` port** from `memorymux.vhd`. The port is declared but never referenced — removing it clarifies the module's actual clock domain.

---

## Conclusion

The PSX_MiSTer core handles CDC reasonably well overall. The most critical crossing (GPU video output async) uses proper 3-FF synchronizers. The phase-aligned PLL relationship between `clk_1x`/`clk_2x`/`clk_3x` allows many crossings to work safely without explicit synchronizers, though this relies on an undocumented assumption.

The main gaps are in `PSX.sv` where a few `clk_1x`-domain signals (`video_isPal`, status bits, `fast_forward`) are used directly in the `clk_vid` domain without synchronization. These are all quasi-static signals with low practical risk, but adding 2-FF synchronizers would be straightforward and would eliminate any theoretical metastability exposure.
